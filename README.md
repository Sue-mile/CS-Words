#### 1. HashCode
- 21 April, 2026
    - HashCode란 객체를 빠르게 찾기 위한 정수값(Hash Value)이다.

    예를 들어, "Apple".GetHashCode()
    를 실행하면 문자열 "Apple"에 대한 정수값이 반환된다.
    
    
    컴퓨터에서 Apple 이라는 이름의 데이터를 하나씩 비교하며 검색하는 Linear Search(순차 탐색) 다소 속도가 느릴 수 있다는 단점이 있다. 따라서 HashCode 를 사용하면 특정 데이터를 정수값으로 변환해, 저장위치를 빠르게 찾을 수 있다.

    - 사용처

    Dictionary, HashSet, Cache(로그인 캐시), DB Indexing, Double Check(중복검사) 등에서 사용된다.

    - 중요한 특징
    "Apple" 이라는 두개의 값이 있을 때, 동일한 HashCode 를 반환한다. 하지만 서로 다른 값이 동일한 HashCode 를 가질 수도 있는데, 우리는 이를 Hash Collision (해시 충돌) 이라고 한다.

    - 결론

    HashCode 는 빠른 검색/분류를 위한 기술이지 절대적인 고유 ID 는 아니다.

        - 참고 : 자료구조, Dictionary 내부 동작, DB Indexing, Cache System 에서 더 자세히 다룬다.

#### 2.CPU와 GPU의 차이
- 22 April, 2026
    - CPU(Central Processing Unit)는 컴퓨터 전반적인 연산과 제어를 담당하는 장치다
    
    기본적으로 복잡한 계산이나 판단 작업에 강하며, 운영체게 실행, 프로그램 처리, 게임 로직, 조건문 처리 등을 담당한다.

    예를 들어, 게임의 AI, 충돌판정, 프로그램 실행, 인터넷 브라우저 동작 등은 대부분 CPU 가 처리한다.

    - GPU(Graphics Processing Unit)는 대량의 단순계산을 동시에 처리하는 장치이다.

    원래는 그래픽 처리를 위해 만들어졌지만, 현재는 영상처리나 AI 연산 등 다양한 분야에서도 사용되고 있다.
    
    예를들어, 게임 그래픽 출력, 그림자 처리, 조명효과, 렌더링, AI 딥러닝 연산 등은 GPU 에서 담당한다.


    - CPU와 GPU의 차이

    | CPU | GPU |
    | --- | --- |
    | 복잡한 계산 | 단순 반복 계산 |
    | 적은 수의 고성능 코어 사용 | 많은 수의 코어 사용 |
    | 판단 및 제어 중심 | 병렬 처리 중심 |
    | 운영체제와 프로그램 관리 | 그래픽 및 대량 연산 처리 |
    

    특히 게임 개발에서는 Unreal Engine 이나 Unity 와 같은 게임 엔진에서는 CPU 와 GPU 가 함께 동작한다.
    주로 Game Engine 에서 CPU 가 담당하는 작업으로는 게임로직, 플레이어 입력 처리, 몬스터 AI, 충돌 판정, 물리 계산 등이 있으며, 
    GPU가 담당하는 작업으로는 렌더링, 배경출력, 이펙트 처리, 조명 및 그림자, 애니메니션 화면 출력 등이 있다.

    - 결론

    CPU 는 복잡한 계산과 제어를 담당하는 장치이며, GPU 는 대량의, 그래픽 및 병렬 연산을 처리하는 장치이다.
    두 장치는 서로 역할이 다르며, 현대의 프로그램과 게임에서는 CPU와 GPU 가 함께 동작하여 성능을 향상시킨다.



#### 3. 소프트웨어의 정의
- 25 April, 2026
    - 소프트웨어(Software)란, 컴퓨터가 하드웨어를 동작시키기 위한 프러그렘과 데이터의 집합이다.

    즉, 사용자가 원하는 작업을 수행할 수 있도록 컴퓨터에게 명령을 전달하는 역할을 한다.
    따라서, 소프트웨어는 눈에 보이지 않는 논리적 구성 요소이며, 하드웨어 없이 단독으로 동작할 수 없다.

    - 하드웨어와 소프트웨어의 차이
    
    | Hardware | Software |
    | --- | --- |
    | 물리적으로 존재 | 비물리적 존재 |
    | 실제 만질 수 있음 | 코드와 데이터 형태로 존재 |
    | CPU, RAM, 키보드 등 | Windows, Unity, Game 등 |
    | 시간이 지나면 마모됨 | 수정과 업데이트 가능 |

    - 소프트웨어의 종류 2가지

    | 시스템 | 응용 |
    | --- | --- |
    | 컴퓨터 자체를 동작이시키 위한 소프트웨어 | 사용자가 특정 작업을 수행하기 위한 소프트웨어 |
    | Windows, MacOs, Linux | Unity, Chrome, Photoshop, Game Program |
    
    - 소프트웨어의 역할
    하드웨어 제어, 사용자 명령 처리, 데이터 저장/관리, 프로그램 실행, 사용자와 컴퓨터 간의 상호작용 제공 등이 있다.

    - 결론
    소프트웨어는 컴퓨터 하드웨어를 동작시키기 위한 프로그램과 데이터의 집합이며, 사용자가 원하는 기능을 수행할 수 있도록 컴퓨터를 제어하는 역할을 한다. 
    


#### 4. 소프트웨어의 특성
- 26 April, 2026
    - 소프트웨어는 하드웨어와 달리 물리적인 형태가 존재하지 않으며, 논리적인 구조로 이루어진 프로그램과 데이터의 집합니다.

    소프트웨어는 개발 이후에도 지속적으로 수정 및 유지보수가 이루어진다는 특징이 있다.

    - 주요 특성
    1. 복잡성 (Complexity)
    
    기능이 많아질수록 구조가 복잡해진다.
    - 코드의 양이 증가할 수록, 버그 발생 가능성의 증가, 유지보수 유지 어려움, 기능 간 의존성이 증가하는 등의 문제가 발생할 수 있다.
    
    2. 비가시성 (Invisibility)
    
    소프트웨어는 눈으로 직접 볼 수 없는 논리적 구조이다.
    - 하드웨어처럼 형태가 존재하지 않기에 내부 구조를 이해하기 어렵다.
    
    3. 변경 가능성 (Changeability)
    
    소프트웨어는 지속적인 수정과 업데이트가 가능하다.
    - 사용자의 오구사항 변화나 버그 수정에 따라 지속적으로 변경된다.

    4. 비마모성 (Non-Wear)

    하드웨어는 시간이 지나면 마모되지만, 소프트웨어는 물리적으로 닳지 않는다.
    - 하지만 잘못된 수정이나 유지보수로 인한 품질 저하 가 이러날 수 있다. 이는 1번 특성과 비슷하다.

    5. 복제 가능성 (Reproducibility)
    
    소프트웨어는 동일한 형태로 무한 복제가 가능하다.
    - 복사 과정에서도 품질 손실이 거의 발생하지 않는다.

    - 결론

    소프트웨어는 복잡성, 비가시성, 변경가능성, 복제가능성 등의 특징을 가지며, 이러한 특성으로 인한 지속적인 관리와 유지보수가 중요하다.

    


#### 5. 소프트웨어 위기
- 27 April, 2026
    - 소프트웨어 위기(Software Crisis)란, 컴퓨터 기술의 발전 속도에 비해 개발 기술과 관리능력이 따라가지 못하면서 발생한 문제를 의미한다.

    해당 개념은 1960년대 후반부터 대형 소프트웨어 프로젝트가 증가함에 따라 등장한 개념이다.

    - 원인

    컴퓨터 하드웨어 성능은 빠르게 발전했지만, 소프트웨어 개발 방식은 체계적이지 못했다.
    
    그로인한 결과, 프로젝트 규모, 코드의 복잡성, 개발 기간이 증가했고, 이에 따른 유지보수가 어려워졌다.

    - 주요 문제점
    1. 개발 일정 지연
    2. 비용 증가
    3. 낮은 품질
    4. 유지보수 어려움
    5. 생산성 저하
    
    이 있으며, 

    - 해결 방안
    소프트웨어공학(Software Engineering) 이 등장하게 되었다.
    
    이를 통해 체계적인 개발 방법, 설계 기법, 테스트 방법, 프로젝트 관리 기술 등이 발전하게 되었다.

    그에 따른 대표적인 기술은 SDLC, OOP, Pattern, Debug, Git 등이 있다.

    - 결론
    소프트웨어 위기는 규모과 복잡성이 증가함에 따라 발생한 개발 및 관리 문제를 의미하며, 지금의 소프트웨어 공학의 발전 및 체계적인 개발 방식의 기반이 됐다.


#### 6. SDLC
- 28 April, 2026
    - SDLC (Software Development Life-Circle)란 소프트웨어를 개발하는 전체 과정을 단계별로 정리한 개발 생명주기를 의미한다.

    이는 소프트웨어를 보다 체계적으로 개발 및 유지보수 하기 위해 사용된다.

    - 목적
    
    개발 과정의 체계화, 일정 및 비용관리, 품질 향상, 유지보수 효율 증가, 프로젝트 위험 감소 가 그 목적이며, 

    1. Requirement Analysis : 사용자가 원하는 기능과 목표 분석
    2. Design : 구조와 동작 방식 설계
    3. Implementation : 코드 구현
    4. Testing : 디버깅 하는 단계
    5. Deployment : 출시
    6. Maintenance : 유지보수

    총 6단계로 구성되어 있으며, 게임 개발에서의 SDLC 를 예시로 들자면 
    | 단계 | 예시 |
    | --- | --- |
    | 요구사항 분석 | 메트로베니아 게임 제작 결정 |
    | 설계 | 맵 구조, 전투 시스템 설계 |
    | 구현 | Unity 코드 작성 |
    | 테스트 | 버그 수정 및 밸런스 테스트 |
    | 배포 | Steam 출시 |
    | 유지보수 | 패치 및 콘텐츠 추가 |
    
    이렇게 되겠다.

    - 결론

    SDLC는 소프트웨어 개발 과정을 보다 체계적으로 관리하기 위한 생명주기 모델이며, 요구사항 분석부터 유지보수까지의 모든 과정을 단계별로 수행함으로써 소프트웨어 품질과 개발 효율을 향상시킬 수 있다.


#### 7.다향성 (Polymorphism)
- 29 April, 2026
    - 하나의 형태가 여러가지 방식으로 동작할 수 있는 객체지향 프로그래밍(OOP)의 특징이다.

    즉, 같은 메서드나 명령이라도 객체에 따라 서로 다르게 동작할 수 있다는 의미이다.

    - 특징
        - 같은 이름의 메서드 사용 가능.
        - 객체 종류에 따른 다른 결과값 출력됨.
        - 코드 재사용돠 유지보수성이 향상된다.

    - 예시
    - 동물 클래스 :
    
            class Animal 
            {
                public virtual void Sound()
                {
                    Debug.Log("동물 소리");
                }
            }




    - 강아지 클래스 : 

            class Dog : Animal
            {
                public override void Sound()
                {
                    Debug.Log("멍멍");
                }
            }

    - 고양이 클래스 : 

            class Cat : Animal
            {
                public override void Sound()
                {
                    Debug.Log("야옹");
                }
            }

        이렇게 세개의 각자 클래스가 있다. 이때, 실행되는 함수는

            Animal animal;

            animal = new Dog();
            animal.Sound();

            animal = new Cat();
            animal.Sound();

        이런식으로 함수가 정해지며, 그에따른 실행 결과는 멍멍 또는 야옹 으로 출력이 될 것이다.

        이 말은 즉, 같은 Sound() 매서드를 호출했지만 객체 종류에 따라 다른 결과라 출렫된다는 걸 알 수 있고 우리는 이를 다형성 이라고 한다.


        - 장점
        1. 공동된 코드를 부모 클래스에서 관리할 수 있어, 코드 재사용성이 증가한다.
        2. 기능 수정 시, 부모 클래스 또는 특정 클래스만 수정하면 돼, 유지 보수에 용이하다.
        3. 새로운 클라스 추가가 쉬워짐으로 인해, 확장성이 증가한다.

        이를 게임 개발에서 활용할 때는 Unity 게임 개발에서는 다형성이 매우 자주 사용된다.
        예를 들면, Enemy, Boss, Weapon, Item, Skill 등과 같은 곳에서 주로 사용되며, 공통된 부모 클래스를 상속받아 서로 다른 방식으로 동작한다.

        - 결론
        다형성은 하나의, 메서드나 객체가 상황에 따라 여러 형태로 동작하는 객체지향 프로그램의 핵심 특징이며, 이를 통해 코드의 재사용과 유지보수 및 확장을 향상시킬 수 있다.



#### 8. 가상화 (virtualization)
- 30 April, 2026
    - 하나의 물리적인 컴퓨터 자원을 여러 개의 가상 환경으로 나누어 사용하는 기술이다.
    즉, 실제 하드웨어 한 대 안에, 여러개의 가상 컴퓨터(Virtual Machine)를 실행할 수 있도록 만드는 기술이다.

    - 목적
    1. 하드웨어 자원 효율 증가
    2. 시스템 관리 효율 증가
    3. 테스트 환경 구축
    4. 비용 절감
    5. 보안 및 안정성 향상

    - 가상머신 (VM)

    가상화 기술을 통해 만들어진 가상의 컴퓨터를 VM(Virtual Machine)이라고 부르며 이는 운영체제 (OS), 메모리 (RAM), 저장공간 (Storage) 등을 독립적으로 사용하는 것처럼 동작한다.

    - 예시
        - Mac PC 안에서 Windows 와 Linux 실행이 가능하다.
        이 말은 즉, 하나의 PC 에서 여러 운영체제를 동시에 운영할 수 있다는 말이된다.

    - 장점
    1. 자원 효율 증가
    2. 테스트 환경 구축
    3. 안정성 향상
    4. 비용 절감

    - 단점
    1. 실제 하드웨어보다 성능 저하 문제 발생할 수 있다.
    2. 많은 메모리와 저장 공간이 필요하다.
    3. 설정 및 관리가 복잡할 수 있다.

    이에 따른 대표적인 가상화 프로그램으로는 VMware, VirtualBox, Hyper-V, Docker(컨테이너 기반의 가상화) 가 되겠다.

    이를 게임에서 활용할 때는, 
    게임 개발 서버에서는 서버를 테스트 하고, 빌드 환경 구성 과 운영체제의 호환성을 테스트 하는 등 가상화 기술이 사용되고 있다.

    - 결론
    가상화는 하나의 물리적인 컴퓨터 자원을 여러 개의 가상 환경으로 나누어 사용하는 기술이다.
    이를 통해 자원 활용과 관리 효율을 높일 수 있으며, 다양한 테스트 및 서버 환경 구축에 활용된다.

#### 9. 추상화

    - 객체나 시스템에서 중요한 특징만 표현, 그 외의 불필요한 세부사항은 숨기는 방법이다.  
    즉, 복잡한 내부 상황을 다 알지 않아도 유저가 필요한 기능을 사용할 수 있게 만드는 것이 그 핵심이다.

    예를 들어 ATM 에서 출금하는데 요구하는 전문적인 기술 같은 것들이 없어도 현금카드와 비밀번호, UI 버튼을 누를 수 있기만 하면 조작할 수 있다.

    - 프로그레밍에서는 클래스, 메소드, 추상클래스, 인터페이스 등을 이용해 추상화를 구현한다.

            abstract class Weapon
            {
                public abstract void Attack();
            }
        Weapon 을 사용하는 코드는 각 무기가 공격을 내부적으로 어떻게 처리하는지 몰라도 Attack()을 호출 할 수 있다.

    |장점|단점|
    |---|---|
    |복잡한 구현을 감출 수 있다.||
    |코드의 역할과 책임이 명확해진다.||
    |변경에 따른 영향을 줄일 수 있다.||
    |코드의 재사용성과 유지보수성이 향상된다.||
    - 결론  
    추상화는 복잡한 대상에서 핵심 기능만 표현하고 세부 구현을 숨기는 객체지향(OOP)의 핵심 개념이다.

#### 10. CBD(Component Based Development)
- 2 May, 2026
    - 소프트웨어를 독립적인 기능 단위인 컴포넌트를 나누고 조립해, 시스템을 개발하는 방식이다.

컴포넌트는 정해진 인터페이스를 통해 다른 컴포넌스와 상호작용 한다.  
잘 설계된 컴포넌드는 내부 구현을 몰라도 사용할 수 있으며, 별도의 프로잭트에서도 재사용이 가능하다.

- Unity 에서의 예시  
GameObject는 Transform, Rigidbody, Collider 등 여러 컴포넌트를 조합해 기능을 만든다.

|장점|
|---|
1. 재사용이 용이하다.
2. 컴포넌트별로 개발과 테스트 진행이 가능하다.
3. 기능 교체와 확장이 비교적 쉽다.
4. 역할이 분리돼 유지보수가 편리하다.

|주의점|
|---|
컴포턴트 간 의존성이 지나치게 많아지면 구조가 복잡해질 위험이 있으므로 각 컴포넌트의 역할과 연결방식을 명확하게 설계해야 한다.

- 결론  
독립적인 컴포넌트를 조립해 소프트웨어를 만드는 개발 방식이며, Unity의 컴포넌트 주고가 그의 대표적인 활용 사례라 볼 수 있다.

#### 11. 결합도
- 3 May, 2026
    - 클래스, 모듈 또는 컴포넌트가 서로 얼마나 강하게 의존하고 있는지를 나타내는 정도이다.

    한 클라스의 변경이 다른 여러 클래스의 수정으로 이어진다면 결합도가 높은 구조라고 할 수 있다.  
    반대로 정해진 인터페이스를 통해 필요한 기능만 주고받는다면 결합도가 낮은 구조에 가깝다.

    |높은 결합도의 문제점|
    |---|
    1. 한 부분의 변경이 다른 부분에 쉽게 영향을 준다.
    2. 개별 테스트가 어려워진다.
    3. 코드 재사용과 기능 교체가 어려워진다.
    4. 전체 구조를 이해하고 유지보수가 어려워진다.

    그렇다면  
    |낮은 결합도를 만드는 방법|
    |---| 
    인터페이스의 사용, 의존성 주입, 이벤트, 명확한 책임 분리 등을 활용할 수 있다.
    예를들어 Player가 특정 Sword 클래스에 직접 의존하는 대신 Weapon 인터페이스에 의존하면 Sword 나 Bow 등으로 쉽게 교체할 수 있다.

    - 응집도와의 관계  
        - 결합도는 모듈 사이의 의존성을 의미한다.
        - 응집도는 허나의 모듈 내부에 있는 기능들이 얼마나 밀접하게 관련돼 있는지를 의미한다.

    일반적으로 낮은 결합도와 높은 응집도를 가진 구조가 좋은 구조로 평가된다.

#### 12. 코드 스멜
- 4 May, 2026
    - 코드가 당장 잘못 동작하는 것은 아니지만, 설계나 유지보수에 문제가 생길 가능성을 보여주는 징후다.

    이 말은 즉, 코드스멜 자체가 버그를 의미하는 것은 아니지만 이를 방치하게 될 경우 이후 기능의 추가 및 수정이 어려워지며, 버그가 발생하기 쉬운 구조가 될 수 있다.

    |대표적인 코드 스멜|
    |---|
    1. 중복코드
        - 같은 로직이 여러 곳에서 반복된다.
    2. 긴 메소드
        - 하나의 메소드에 과대한 양의 일을 처리한다.
    3. 거대한 클래스
        - 하나의 클래스가 지나치게 많은 책임을 갖는다.
    4. 매직 넘버
        - 의미를 알 수 없는 숫자가 코드에 직접 사용된다.
    5. 과도한 매개변수
        - 하나의 메소드가 너무 많은 값을 전달받는다.
    6. 산탄총 수술
        - 작은 기능 하나를 변경하기 위해 여러 파일을 수정해야 한다.

    이와 같은 문제들을 개선하기 위해서는  
    코드의 동작을 확인할 수 있는 테스트를 준비, 메소드 추출, 이름 변경, 클래스 분이, 중복 제거 등의 리팩토링을 수행해야 한다.

#### 16. 추상클래스(Abstract Class)
- 8 May, 2026
    - 직접 객체를 생성할 수 없으며, 여러 자식 클래스가 공유할 공통 기능과 반드시 구현해야 할 기능을 정의하는 클래스이다.

        abstract class Enemy
        {
            public int Health {Get; protected set; }

            public abstract void Attack();

            public void TakeDamage(int damage)
            {
                Health -= damage;
            }
        }

        class Slime : Enemy
        {
            public override void Attack()
            {
                print("슬라임 공격");
            }
        }

    Enemy 자체는 new Enemy() 를 사용해 생성할 수 없지만 Slime 과 같은 자식 클래스는 Enemy의 공통 기능을 상속받고 Attack() 을 각자의 방식으로 구현할 수 있다.

    |사용목적|
    |---|
    1. 여러 클래스의 공통 상대화 기능을 한 곳에서 관리한다.
    2. 자식 클래스가 특정 기능을 반드시 구현하도록 한다.
    3. 다형성을 활용할 수 있는 공통 타입을 제공한다.

#### 17. 인터페이스(Interface)
- 9 May, 2026
    - 클래스가 제공해야 할 기능의 규칙, 즉 계약을 정의하는 타입이다.

            interface IDamageable
            {
                void TakeDamage(int damage);
            }
            class Player : IDamageable
            {
                public void TakeDamage(int damage)
                {
                    print($"플레이어가 {damage}의 피해를 입음");
                }
            }
            class BreakableBox : IDamageable
            {
                public void TakeDamage(int damage)
                {
                    print("상자가 파괴됨");
                }
            }
    Player 와 BreakableBox 는 서로 다른 클래스지만 두 클래스 모두 IDamageable을 구현하므로 공격 시스템에서는 같은 피해 대상으로 처리할 수 있다. 

    - 추상 클래스와의 차이

    |구분|추상클래스|인터페이스|
    |---|---|---|
    |목적|공통 상태과 구현 공유|공통 동작의 계약 정의|
    |상속|상속 및 구현한 클래스만 상속 가능|여러 인터페이스 구현 가능|
    |공통 필드|가질 수 있음|인스턴스 필드를 가질 수 없음|
    |적합한 경우|밀접한 클래스 계층|서로 다른 타입에 같은 기능 부여|

#### 18. 유즈케이스 다이어그램(Use Case Diagram)
- 10 May, 2026
    - 사용자의 관점에서 시스템이 제공해야 하는 기능과 외부 대상의 관계를 표현하는 UML 다이어그램이다.

    시스템 내부의 코드 구조보다는  
    누가 어떤 기능을 사용하는가? 를 이해하는데 목적성을 둔다.

    |주요 구성 요소|
    |---|
    1. Actor
        - 시스템과 상호작용하는 사용자 또는 외부 시스템이다.
    2. Use Case
        - 시스템이 사용자에게 제공하는 기능이다.
    3. System Boundary
        - 표현하려는 시스템의 범위를 나타낸다.
    4. Relationship
        - Actor 와 Use Case 또는 Use Case 사이의 관계를 나타낸다.
    5. unclude, extend, generalization
        - Use Case 사이의 포함, 확장 또는 일반화 관계를 나타낸다.

    이를 게임으로 예시를 든다면,  
    Player 라고 하는 Actor 가 로그인, 게임 시작, 아이템 구매 라고 하는 Use Case 를 사용한다고 표현할 수 있다. 
    이때, 아이템 구매가 항상 결제 처리를 필요로 한다면 include 관계를 사용할 수 있다.

    다만 주의점으로는 
    Use Case Diagram 은 기능의 처리 순서나 클래스 내부 구조를 설명하지 않으며 처리 순서는 시퀀스 다이어그램, 정적인 코드 구조는 클래스 다이어그램으로 표현하는 것이 적합하다.

#### 19. 클래스 다이어그램(Class Diagram)
- 11 May, 2026
    - 시스템을 구성하는 클래스의 구조와 클래스 사이의 관계를 표현하는 UML 다이어그램이다.

    일반적으로 프로그램의 정적인 구조를 보여주며, 객체지향 시스템을 설계하거나 기존 코드를 이해할 때 사용한다.

    |클래스의 기본 표현|
    |---|
    1. 클래스 이름
    2. 속성 또는 필드
    3. 메소드

    |접근 제한자|
    |---|
    1. public 은 + 로 표기한다.
    2. private 은 - 로 표기한다.
    3. protected 는 # 로 표기한다.

    |주요 관계|
    |---|
    1. 연관(Association)
        - 객체가 다른 객체를 알고 있거나 사용하는 관계이다.
    2. 상속(Generalization)
        - 자식 클래스가 부모 클래스의 기능을 상속하는 관계이다.
    3. 집합(Aggregation)
        - 전체와 부분이 약하게 연결된 관계이다.
    4. 합성(Composition)
        - 부분의 생명주기가 전체에 강하게 종속된 관계이다.
    5. 의존 (Dependency)
        - 한 클래스가 다른 클래스를 일시적으로 사용하는 관계이다.
    이러한 관계의 끝에는 1, 0, .1, 1. ... 와 같은 다중성을 표시해 연경 가능한 객체의 수를 나타낼 수 있다.

    게임으로 예를 들자면 
    Player class 가 여러개의 Item 을 보유한다면 Player 와 Item 사이를 1 : 0 의 관계로 표현할 수 있다.  
    Warrior 가 Player 클래스를 상속한다면 두 클래스를 상속 관계로 표현할 수 있다.

#### 20. 시퀀스 다이어그램(Sequence Diagram)
- 12 May,2026
    - 객체나 시스템 구성 요소가 특정 기능을 수행하면서 메세지를 주고받는 순서를 시간의 흐름에 따라 표현하는 UML 다이어그램이다.

    클래스 다이어그램이 정적인 구조를 보여준다면, 시퀀스 다이어그램은 실행 중의 동적인 상호작용을 보여준다.

    - 시간은 일반적으로 위에서 아래 방향으로 흐른다.

    |주요 구성 요소|
    |---|
    1. Participant or Actor
        - 상호작용에 참여하는 대상이다.
    2. Lifeline
        - 참여 대상이 존재하는 시간을 나타내는 세로선이다.
    3. Message
        - 메소드 호출이나 데이터 전달을 나타낸다.
    4. Return Message
        - 작업을 처리한 결과가 반환되는 것을 나타낸다.
    5. Activation
        - 대상이 실제로 작업을 수행하는 구간이다.
    6. alt, opt, loop
        - 조건 분기, 선택 실행 및 반복 처리를 나타낸다.

    이를 게임으로 예를 들자면,  
    플레이어가 공격 버튼을 누르면 PlayerController 가 Weapon 의 Attack() 함수를 호출한다.  
    Weapon 은 Enemy 의 TakeDamage() 함수를 호출하고, Enemy 는 자신의 체력을 갱신한다.  
    시퀀스 다이어그램을 사용하면 이런 호출 순서를 시간의 흐름에 따라 표현할 수 있다.
